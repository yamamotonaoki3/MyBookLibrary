### 2026-10-26: 公開認証画面の判定をproxyとクライアントの強制リダイレクトで共有する

- **種別**: Codexレビュー採用（Issue #782 / PR #785）

- **何が起きたか**: ブラウザを閉じた後の古いトークンでセッションAPIは認証済み、proxyは未ログインになる。強制パスワード変更のガードがログイン画面だけを除外すると、登録・パスワードリセット画面から変更画面、ログイン画面への循環が起きる。

- **状態**: 有効

### 2026-10-25: PWAは本番SWで登録・キャッシュ・移行を検証し、既定ルールの混入を防ぐ

- **種別**: 手直し（Issue #776 PWAビルド依存）
- **対象領域・関連ファイル**: PWA / `app/next.config.ts`、`app/src/auth.config.ts`、`app/src/lib/pwaRuntimeCaching.ts`、`app/pwa-worker/index.js`、`app/e2e-pwa/cache-isolation.spec.ts`

- **対応**: SWとハッシュ付き依存スクリプトだけを公開し、API・類似パスは拒否する。start-urlと既定ルールを無効化し、個人データをNetworkOnly、公開資産を明示したルールへ限定する。activate時に既知の旧個人キャッシュだけを削除する。本番E2Eで実ログイン・2ユーザー切替・CacheStorage・オフライン・旧キャッシュ移行を検証した。

- **状態**: 有効

### 2026-10-22: Dockerの実行ステージでもロックファイルを使い、ローカル設定はビルド対象から除外する

- **種別**: 手直し（Issue #770 Docker再ビルド）
- **対象領域・関連ファイル**: Docker / `app/Dockerfile`、`app/.dockerignore`
- **何が起きたか**: ビルドステージの `npm ci` とNext.jsビルドは成功したが、実行ステージの `npm install --no-save prisma dotenv` が依存を再解決し、ロック済みNext.jsと新しいOpenNextのpeer dependency競合で失敗した。また、`.dockerignore` がなく、ローカル設定や生成物までDockerへ送る構成だった。
- **対応**: 実行ステージにも元のpackage.json・package-lock.json・Prisma設定を渡し、`npm ci --omit=dev` とpostinstallで同じ依存・クライアントを導入した。Node.jsは両ステージで22.23.4に固定し、ローカルの秘密設定・依存・生成物を除外した。完成イメージのNode.js・PrismaとHTTP疎通、ビルドステージの設定除外を実物で検証した。
- **次回の行動規則**: Dockerの全ステージで依存の導入元とlockfileの有無を確認する。既存のビルド用lockfileがあっても、実行ステージの追加インストールがそれを使うとは限らない。Dockerfile変更の検証は、next devを対象とする既存E2Eに任せず、完成したイメージを起動して行う。
- **追記（#776）**: file依存ではvendorとプロジェクト.npmrcも全ステージのnpm ci前に配置する。元のnode_modulesがないprod-only導入と完成イメージの実体を確認する。上流配布物をハッシュ付きで保持する場合は、Windowsのcore.autocrlfによる改行変換も対象ディレクトリの.gitattributesで防ぎ、Gitのフィルター適用後もバイト列が一致することを照合する。

### 2026-10-22: 外部書籍の照合は候補取得と比較の条件を揃え、表記ゆれ対応のために全件走査を追加しない

- **種別**: Codexレビュー採用（Issue #768 公開レビュー件数）
- **対象領域・関連ファイル**: 書籍照合 / `app/src/repositories/bookReviewRepository.ts`、`app/src/lib/bookReviewSummary.ts`
- **何が起きたか**: DBではタイトルの完全一致で候補を取り、取得後だけNFKC・空白除去で比較していたため、表記ゆれした本を候補取得の段階で見落とした。候補取得をモックした単体テストだけでは発見できなかった。著者一覧の全件取得で補う案は、検索ページの件数に関係なく著者総数・著作数に応じた読み込みを追加してしまった。
- **対応**: ユーザー承認によりDB変更なし・ISBN優先・未解決時はタイトルと著者の完全一致に限定した。代表外ISBNも照合し、ISBNで解決済みの結果はタイトル照合を省略する。実Repositoryを使うMySQL・D1結合テストと、著者全件取得を行わない単体テストを追加した。
- **次回の行動規則**: 候補を取得するDB条件と、取得後の一致判定は同じ照合仕様にする。表記ゆれを吸収する必要がある場合は、全件走査で補う前に索引付きの正規化データが必要かを計画段階で判断する。候補取得をモックしたテストに加え、単独の検索結果から実DBで対象を引けるかを確認する。
- **状態**: 有効
- **根拠**: Issue #768、追加レビュー2件、実DBでのRED/GREEN、ユーザーによる照合範囲の承認


### 2026-10-21: 図書館確認の共通化ではISBN-10の互換処理も引き継ぐ

- **種別**: Codexレビュー採用（Issue #766 貸出チェックの全画面統一）
- **対象領域・関連ファイル**: 図書館確認 / `app/src/lib/libraryAvailabilityQuery.ts`、`app/src/lib/isbn.ts`
- **何が起きたか**: 一覧・検索の確認先を全版確認APIへ統一した際、従来の単一ISBN用APIにあったISBN-13からISBN-10への変換・併用が失われた。ISBN-10でしか蔵書を返さない図書館では、貸出可能でも蔵書なしになった。
- **対応**: 各版のISBNと変換可能なISBN-10を併せて問い合わせ、同じ版の結果を図書館システム・館キー単位で統合した。表示キーは登録された版のISBNを維持し、ISBN-10のみが貸出可を返す退行テストで確認した。
- **次回の行動規則**: 画面やAPIを共通化するときは、移行元の入力補完・互換処理・結果統合も比較する。カーリルの版別確認ではISBN-13/10を同じ版へ統合し、別の版の結果とは混ぜない。
- **状態**: 有効
- **根拠**: Issue #766、Codexレビュー指摘とAPI退行テスト

### 2026-10-11: 外部APIのタイムアウトは「本文の読み取り」と「ページング全体」まで含めて設計する

- **種別**: Codexレビュー採用（Issue #634 読書ステータス保存のAPI遅延対策）
- **対象領域・関連ファイル**: バックエンド / `app/src/lib/rakuten.ts`（`fetchRakutenWithRetry`・`searchBooks`）、`app/src/lib/requestSignal.ts`
- **何が起きたか**:
  1. `fetch(url, { signal })` のタイムアウトは、ヘッダ受信後の本文ストリームにも効く。ヘッダは即返るが本文が遅いと、`fetch()` 自体は成功し、呼び出し側の `res.json()` が `AbortError` で reject して、リトライ・フォールバックを素通りして画面まで例外が伝わった。
  2. `searchBooks` が複数ページを取得する際、`totalTimeoutMs`（リトライを含む1呼び出しの上限）を各ページの呼び出しごとに作り直していたため、「全体で20秒」のつもりがページ数倍（理論上は数十分）まで伸びる設計になっていた。
- **対応**: `fetchRakutenWithRetry` が本文のJSON読み取りまで try/リトライの範囲に含め、パース済みJSONを返す形に変更した。`searchBooks` は呼び出し全体で1つの期限シグナルを作り、各ページへ共有してループも期限切れで打ち切る。それぞれ単体テスト（ヘッダ即時・本文遅延／ページ2以降が無応答）を追加した。
- **次回の行動規則**:
  - 外部APIクライアントにタイムアウトを入れるときは、**レスポンス本文の読み取りが同じ try の中にあるか**を確認する（Response を返す設計だと呼び出し側の本文読み取りが無防備になる。パース済みデータを返すか、本文読み取りまでをヘルパー内に閉じる）。
  - 「全体の上限」を意味するオプションは、**複数リクエスト（ページング・リトライ）をまたいで1つの期限**として共有する。リクエストごとに新しいタイマーを作らない。
  - タイムアウトのテストは「接続が張られない」ケースだけでなく、「ヘッダ即時・本文遅延」「2ページ目以降が無応答」のケースも作る。
- **状態**: 有効
- **根拠**: Issue #634、Codexレビューの指摘（2件）

### 2026-09-29: E2E 前にポート3100が別ワークツリーの残存サーバーでないか確認する

- **種別**: 手直し（Issue #621 Vercel 関連削除の E2E 検証中）
- **対象領域・関連ファイル**: E2E / `app/playwright.config.ts`（`webServer.reuseExistingServer: !process.env.CI`）
- **何が起きたか**: `e2e/notifications.spec.ts` の cron 系2件が 500 で失敗した。原因は、別ワークツリー（`chore-613-layer-boundaries`）で過去に起動された E2E 用 `next dev -p 3100` が残っており、Playwright がそれを再利用していたこと。E2E は他ブランチのコードと、そのワークツリーの `.env.test` で実行されていた（成功した他のテストも本ブランチの検証になっていなかった）。また同一ワークツリーで別ポートの `next dev` が動いていると「Another next dev server is already running」で webServer 自体が起動しない。
- **対応**: 残存プロセスの起動元（コマンドライン）を確認してから停止し、再実行して15件成功を確認した。
- **次回の行動規則**:
  - **ローカルで E2E を実行する前に、ポート3100（とスタブの3999）を使っているプロセスの有無と起動元ディレクトリを確認する**（例: `netstat -ano | grep ':3100 .*LISTEN'` → PID のコマンドラインを確認）。別ワークツリーのものなら停止してから実行する。
  - 動作確認用に自分で起動した `next dev` は、確認が終わったら必ず停止する（同一ワークツリーの2つ目の `next dev` は起動できない）。
  - E2E が「環境変数由来に見える」失敗（500・認証不一致など）をしたら、コードを疑う前に再利用されたサーバーを疑う。
- **状態**: 有効
- **根拠**: Issue #621

### 2026-08-15: Next.js 16のfavicon実装は自作ICOのBMPデコード非対応と`metadata.icons`の上書きに注意

- **種別**: 手直し（Issue #525 アプリアイコンをファビコンとして使用する対応中）
- **対象領域・関連ファイル**: フロントエンド / `app/src/app/icon.png`、`app/src/app/layout.tsx`
- **何が起きたか**:
  1. アプリアイコン（`public/icon-source.png`）から16x16/32x32/48x48のPNGを生成し、PNGバイナリをそのままICOコンテナに格納する形式（Windows Vista以降対応の一般的な方式）で`favicon.ico`を自作したところ、Next.js 16.2.6 (Turbopack)のビルド時画像処理が `Processing image failed / The decoder for Bmp does not support the format features Unknown bitmap header type` というエラーで失敗した。Turbopackの内蔵デコーダはICO内のBMP形式のみ対応しており、PNG格納形式のICOはサポート外だった。
  2. 対策として`favicon.ico`をやめ、Next.jsのfile convention `app/icon.png`（単純なPNGファイル）に切り替えたところビルドエラーは解消したが、`.next`キャッシュ削除・devサーバー再起動を行ってもHTMLに`<link rel="icon">`が出力されなかった。原因は`app/src/app/layout.tsx`の`metadata.icons`で`apple: "..."`のみを明示指定していたこと。Next.jsは`metadata.icons`が明示されると、file convention（`icon.png`等）による自動注入が働かなくなる。
- **対応**: `favicon.ico`ではなく`app/icon.png`を配置し、`layout.tsx`の`metadata.icons`に`icon: "/icon.png"`を`apple`と併記することで、両方のアイコンがHTMLに正しく出力されるようにした。
- **次回の行動規則**:
  - **Next.js 16 (Turbopack) でfaviconを自作ICOとして用意する場合、PNG格納形式のICOはビルド時にデコードエラーになる。** favicon用に複数サイズを1ファイルにまとめたい誘惑があっても、`.ico`を自作するのではなく、Next.jsのfile convention（`app/icon.png`、`app/icon.svg`等）を使う方が安全。
  - **`layout.tsx`（または各セグメントのlayout/page）の`metadata.icons`に何か1つでもキー（`apple`等）を明示すると、file conventionによるicon自動検出が働かなくなる。** `icon.png`等のfile conventionを使うファビコン・アプリアイコンを追加/変更したら、`metadata.icons`にコンフリクトする明示指定が無いか、またはその明示指定に新しいアイコンのキーが漏れていないか必ず確認する。
- **状態**: 有効
- **根拠**: Issue #525

### 2026-08-15: Notificationの一意制約設計と、DB直列化にFOR UPDATEを使う際の落とし穴

- **種別**: Codexレビューで採用された指摘（Issue #521 相互フォロー成立後の活動通知の実装中）
- **対象領域・関連ファイル**: バックエンド / `app/prisma/schema.prisma`（`Notification`モデル）、`app/src/app/api/reading-status/route.ts`、`app/src/app/api/favorite-authors/route.ts`、`app/src/app/api/admin/reviews/[id]/route.ts`
- **何が起きたか**:
  1. `Notification`には既存の`@@unique([userId, type, bookIsbn])`があり、これは「本ごとに1件のnew_book/review_deleted通知」を保証するための設計。新しい通知種別（相互フォロー相手の読みたい本追加）で「誰が追加したか」を区別しようとして`actorId`を一意制約に追加するマイグレーションを行ったところ、`actorId`が常にnullの既存通知種別（`new_book`）でMySQLがNULL同士を別値扱いするため、cronの重複防止が効かなくなる副作用（DBレベルの重複防止の後退）が生じた。

- **対象領域・関連ファイル**: 認証 / `app/src/lib/sessionPolicy.ts`、`app/src/lib/sessionJwt.ts`、`app/src/auth.config.ts`
- **何が起きたか**:
  - 「ログイン保持なし」のセッションを短くするため、トークンの `exp` を設定しようとした。しかし Auth.js の `encode` は、トークンを発行するたびに `exp = now + maxAge` で上書きする。さらに、セッション取得のたびに再発行（スライディング）されるため、`token.exp` を設定しても効かない。
  - Jest は CommonJS で、`next-auth/jwt` などの ESM のパッケージを、静的に import できない。
- **対応**: `jwt.encode` を差し替え、トークンの `rememberMe` に応じた `maxAge` を渡した（#737）。ESM のパッケージは動的に import し、テストでは mock した。ビルドした Worker で、本物の JWT を復号して、期限を確認した。
- **次回の行動規則**:
  - ライブラリの内部の挙動（上書き・再発行）は、ソースで確認してから設計する。
  - 有効期限のような値は、設定ファイルやテストだけでなく、**ビルドした実物から、実際の値を取り出して確認する**。
- **状態**: 有効
- **根拠**: Issue #736 / #737、PR #740 / #741

### 2026-10-17: Windows で、`wrangler d1 execute --command` に複数行の SQL を渡すと失敗した。1 行にするか、`--file` を使う

- **種別**: 手直し（環境差）
- **対象領域・関連ファイル**: 運用・テストデータ / `wrangler d1 execute`
- **何が起きたか**: Windows で、`--command` に複数行の SQL を渡すと失敗した。また、`--persist-to` のパスが長いと、wrangler / miniflare が保存に失敗した。
- **対応**: 複数文の SQL は、`--file` で渡した。ローカルの D1 の保存先は、短いパス（`C:/tmp/...`）にした。
- **次回の行動規則**: Windows では、`--command` に複数行の SQL を渡さず、1 行にするか `--file` を使う（`--command` が複数文を扱えないわけではなく、今回の環境で複数行の引数が失敗した、という観測）。`--persist-to` は短いパスにする。
- **状態**: 有効
- **根拠**: Issue #738 の作業

デバッグ手法として有効だったもの（参考）:
- `window.fetch`をモンキーパッチして実際に飛んだリクエストのURL/methodをログする。chrome-devtools MCPの`navigate_page`の`initScript`パラメータを使うとページ読み込み前・アプリコードより先に仕込める。
- `console.log`を一時的に仕込み、`list_console_messages`に`includePreservedMessages: true`を付けて確認する（reloadやSPA遷移でconsoleがクリアされるため、これを付けないと過去のログが消えて見えない）。
- サーバー側ロジックが正しいかは、ブラウザを介さず`curl`でCSRFトークン取得→ログイン→session update POSTの一連の流れを再現して検証すると、クライアント側の問題かサーバー側の問題かを素早く切り分けられる。

### 2026-10-24: WorkerdのLinuxスモーク検証にはglibc環境を使う
- **種別**: 手直し（Issue #774 Next.js / OpenNext更新）
- **対象領域・関連ファイル**: Cloudflare Worker / app/package.json、LinuxコンテナでのWorker検証
- **何が起きたか**:

  - Debian BookwormベースではOpenNextのWorkerビルドとログイン・D1・Cronを含むHTTPスモーク10件が成功した。
  - npmは依存パッケージの未承認install scriptを警告するため、Worker実行に必要なworkerdだけ、解決済みバージョン1.20261006.1をallowScriptsで許可した。
- **再発防止**: WorkerのLinux実行検証はglibc 2.35以上の環境で行う。npm install scriptを許可する場合は依存全体を一括許可せず、必要なパッケージとバージョンに限定する。
- **状態**: 有効
- **根拠**: Issue #774のWorker build/smoke。Cloudflare WranglerのLinux要件（glibc 2.35以上）。

### 2026-10-26: サーバーが見えない情報（sessionStorage）で判定していると、サーバーとブラウザの判断がずれてちらつく。Auth.js のセッション取得は Cookie を再発行するため、Cookie 削除に頼る片付けは競合する
- **種別**: 手直し（Issue #782 ログイン保持なしのちらつき）
- **対象領域・関連ファイル**: 認証 / app/src/auth.config.ts、app/src/lib/sessionPolicy.ts、app/src/app/_components/Providers.tsx
- **何が起きたか**:
  - 「ブラウザを閉じたらログアウト」を `sessionStorage` だけで判定していた。サーバー（proxy）には届かないため、サーバーは「ログイン済み」としてダッシュボードを返し、あとからブラウザ側が `signOut` してちらつきが出た。
  - 古いトークンをクライアントの `signOut` で片付けようとしたが、サインアウト直後の `/api/auth/session` の応答が `authjs.session-token` を再発行し、Cookie が復活した（Issue #784 と同じ競合）。
  - Codex レビューで、パスワード変更の強制リダイレクトが、ログイン画面で循環する指摘を受けた。
- **対応**: ブラウザを閉じると消える目印の Cookie をログイン時に発行し、proxy が「トークンが保持なしで目印がなければ未ログイン」と判定するようにした。古いトークンの片付けはやめ（proxy が拒否し続けるので害がない）、ログイン画面ではパスワード変更画面へ移さないようにした。
- **次回の行動規則**: 認証状態の判定は、サーバーが受け取れる情報（Cookie / ヘッダー）で行い、ブラウザ内の記憶（`sessionStorage` / `localStorage`）だけに頼らない。Auth.js の `/api/auth/session` は Cookie を再発行するので、同時に飛んでいるセッション取得があると、Cookie 削除が取り消される。削除の成否を前提にした設計にしない。Auth.js の `authorized` で Cookie を消しても、直後にセッション応答の Set-Cookie が追記されるため効かない。
- **状態**: 有効
- **根拠**: Issue #782 / #784、Codex レビュー
