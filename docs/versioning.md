# バージョンの付け方と基準

アプリのバージョン番号（`app/package.json` の `version`）を、どう付け、いつ上げるかを定める。番号は `/api/version` の `name` と、`tag`（`<バージョン>-<コミット7文字>`）に出る（[cloudflare-deploy.md](cloudflare-deploy.md#稼働中のバージョンの確認apiversion)）。

## 形式

`MAJOR.MINOR.PATCH`（[セマンティック バージョニング](https://semver.org/lang/ja/)に沿う）。現在は `0.x`（正式版の前）なので、**MAJOR は `0` のまま**とし、実質的に「MINOR が大きな区切り、PATCH が小さな修正」として扱う。

| 桁 | 上げる条件 | 例 |
| --- | --- | --- |
| MINOR（`0.N.0`） | 次のいずれかを、本番へ出す区切り。上げたら PATCH は `0` に戻す | 利用者に見える機能の追加・変更。D1 のスキーマ変更（マイグレーションの追加）。実行基盤に影響する依存のメジャー更新（Prisma、Next.js、React、認証、OpenNext など）。Cron などの運用上の挙動の変更 |
| PATCH（`0.N.P`） | 利用者に見える不具合の修正、小さな依存の更新（パッチ・マイナー）など、挙動の区切りにならない変更 | スキャナ画面の不具合修正。依存のパッチ更新 |
| MAJOR（`1.0.0`） | 「正式版」と判断したとき。基準は、そのときに別途決める | — |

### 上げない変更

ドキュメントだけの変更、テストだけの変更、CI や開発用の設定だけの変更は、利用者の挙動が変わらないので上げない。

### 迷ったとき

- 本番のデータやスキーマに触れる、または戻しにくい変更なら MINOR。
- 利用者から見て「直った」だけなら PATCH。
- 判断がつかなければ、PR に理由を書いて相談する。番号は後から細かく直せないので、小さく上げすぎない。

## いつ・どう上げるか

1. **本番へ出す前（`main` → `production`）に、`main` で上げる。** 本番へ出す区切りごとに 1 回で、PR ごとには上げない。ステージングは `main` の番号を出すので、ステージングの確認時点で、本番に出す番号が分かる。
2. `app/` で次のコマンドを実行する（`package.json` と `package-lock.json` が更新される。Git のタグは作らない）。

   ```bash
   npm version <patch|minor> --no-git-tag-version
   ```

3. 上げる PR には、Issue と、上げる理由（上の表のどの条件か）を書く。この文書の「履歴」にも 1 行足す。
4. 本番へ出したあと、`/api/version` の `name` が新しい番号になっていることを確認する。

### 本番だけに急ぎの修正を出す場合

`main` に先に修正を入れて、`production` へ取り込む（または同じ修正を取り込む）。そのとき PATCH を上げ、同じ上げを `main` にも入れる。`production` だけ番号が進む状態を残さない。
