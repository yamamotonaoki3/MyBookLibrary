# 運用手順書

公開後の運用（日々の確認・障害時の初動・復旧・秘密情報の更新）をまとめる。構成は [アーキテクチャ概要](architecture.md)、デプロイとロールバックのコマンドは [Cloudflare へのデプロイ](cloudflare-deploy.md) を参照する。この文書は、それらを繰り返さず、**何を、いつ、どう判断するか**を書く。

> **実行するのは所有者本人です。** 本番の操作（`wrangler`・Cloudflare のダッシュボード・Google のコンソール）は、本人が行う。パスワード・secret・メールアドレス・トークンなどの値は、チャット・Issue・PR・コミットに書かない（出力を共有するときは、値を伏せる）。本番のデータを書き換える操作は、実行前に、対象と範囲を確認する。

## 1. 日々の確認

公開後の**最初の 1 週間**は毎日、その後は**週に 1 回**を目安にする。見る場所は、Cloudflare のダッシュボード。**普段の水準**は、最初の 1 週間で把握し、それとの差で判断する（固定のしきい値は決めていない）。

| 確認 | 見る場所 | 正常 | 異常なとき |
| --- | --- | --- | --- |
| リクエストとエラー率 | Workers & Pages → `mybooklibrary` → Metrics | エラー率が、普段の水準 | 「4. 障害時の初動」へ |
| CPU 時間 | 同上 | 普段の水準。急に増えていない | ログで、重い処理を探す。直近のデプロイが原因なら、ロールバック（「5」） |
| ログのエラー | `mybooklibrary` → Observability（または `npx wrangler tail`） | `error` レベルが、ほぼない | 内容を確認（「4」）。秘密の値が出ていないか、共有前に確認する |
| リクエストをまたぐ Promise の例外（hung） | 同上。`hung`、別のリクエストの I/O を使った旨の例外・警告を探す | 出ていない | 日時と URL（個人情報を含めない）を控え、新しい Issue にする（関連: #734。原因の Promise は特定できていない） |
| 新刊チェックの Cron | `mybooklibrary` → Logs（毎日 JST 09:00 の実行） | 成功している | `CRON_SECRET`・楽天 API を確認（「4」の「新刊通知が来ない」） |
| D1 の使用量 | Workers & Pages → D1 → `mybooklibrary-db` | 読み書きの行数・容量が、普段の水準 | 急増なら、ログで、原因のクエリを探す |
| 請求 | アカウント → Billing | 想定の範囲 | 請求アラート（#682）の設定を確認 |
| 稼働中のバージョン | `curl https://mybooklibrary.nyproducts.workers.dev/api/version` | `tag` が、意図したコミット | ずれていれば、デプロイ履歴を確認 |

- PowerShell では、`curl` ではなく `curl.exe` と書く（`curl` は `Invoke-WebRequest` の別名）。
- **本番で、書き込みを伴う自動テスト（E2E など）は実行しない。** ステージングの疎通確認（`npm run smoke:remote`）も、ステージング専用。

## 2. 定期的な作業

| 作業 | 頻度の目安 | 内容 |
| --- | --- | --- |
| 公開後の監視 | 公開から 1 週間、毎日 | 「1」の全項目 |
| 依存パッケージ・Node の更新 | 必要に応じて | 通常の PR の流れ（Issue → PR → CI → ステージング → 本番） |
| secret の更新 | 漏えいの疑いがあるとき、メンバーの変更時、または年 1 回程度（推奨） | 「7」 |
| GitHub・Cloudflare アカウントの保護 | 初回と、変更時 | **2 段階認証（2FA）を、両方で有効にしている**（2026-10-18 に確認）。Cloudflare は、API トークンの権限・不要なトークンの削除も確認する。「9」 |
| 暗号化ダンプの保管 | 初回と、保管先を変えたとき | `app/prisma/scripts/migration/dumps/` の暗号化ダンプ（`.enc`）を、2 か所（この PC と USB）に保管している。**3 か所目は未実施（任意）** |

- **D1 の定期エクスポートは、未実装**。現状の復元の手段は、D1 Time Travel（時点復元。有料プランで 30 日保持）。計画は [移行計画（アーカイブ）](archive/cloudflare-d1-migration-plan.md) の P4-8。

## 3. デプロイ

通常の流れと、コマンドは [Cloudflare へのデプロイ](cloudflare-deploy.md)。要点だけ示す。

1. PR を `main` にマージ → ステージングへ自動デプロイ。
2. ステージングで確認する（画面、`/api/version`）。
3. 問題がなければ、`main` を `production` ブランチへ反映する（早送り。強制はしない）。

   ```bash
   git fetch origin
   git push origin origin/main:production
   ```

4. Cloudflare のダッシュボード（Workers & Pages → `mybooklibrary` → Deployments）で、ビルドの成功を確認する。
5. `/api/version` の `tag` が、反映したコミットになっていることを確認する。

- デプロイのたびに、**リモートの D1 へ、マイグレーションが適用される**。破壊的なマイグレーション（列の削除など）は、公開前に、ステージングで確認する。
- 本番へ反映した直後は、画面を開き、主要な操作（ログイン・一覧・管理者画面）を、データを変更しない範囲で確認する。

## 4. 障害時の初動

まず、**直前に何が変わったか**（デプロイ・secret の変更・外部サービスの障害）を確認する。

1. `/api/version` と、Deployments の履歴で、直前のデプロイを確認する。
2. ダッシュボードの Metrics と、ログで、エラーの内容を確認する。
3. 直前のデプロイが原因なら、**ロールバック**（「5」）。原因が分からなければ、先にロールバックして、そのあと調べる。
4. Cloudflare 側の障害が疑われるときは、Cloudflare の公式のステータスページを確認する。

| 症状 | 確認すること |
| --- | --- |
| サイト全体が 5xx | 直前のデプロイ → ロールバック。D1 のエラーがログに出ていないか |
| ログインできない | `AUTH_SECRET` を変えていないか（変えると、全員が再ログインになる）。10 回失敗で 15 分ロックされる。Google ログインなら、リダイレクト URI の登録（環境ごと） |
| 画面が「This page couldn't load」になる | ログのエラー。API の失敗が原因のことが多い。件数が増えたときに、D1 の変数の上限（100 個）に当たる（過去: 管理者画面、#744）。hung の例外なら、「1」の対応 |
| 本の検索で結果が出ない | 楽天の 403（許可された Web サイトの登録、`RAKUTEN_ALLOWED_ORIGIN`）、429（アクセス過多）。**楽天が 403 のとき、アプリは NDL の結果に切り替わるため、結果が出ていても、楽天が通っているとは限らない** |
| 新刊通知が来ない | 毎日 JST 09:00 の Cron のログ。`CRON_SECRET` の登録（Worker ごとに別の値）。楽天 API の状態 |
| 管理者画面が開かない | `/api/admin/*` のどれが失敗しているか（画面の上部に、読み込めなかったデータが出る）。ログで、該当 API のエラーを確認 |
| データの誤更新・破損 | 「6」。**書き込みを止めてから**、現状を保全する |

- 原因が分かったら、Issue にする（値・個人情報は書かない）。再発を防ぐ学びは、[lessons-learned](lessons-learned.md) に記録する。
- **本番の D1 を直接書き換えるのは、最後の手段。** 実行前に、対象の行の件数と条件を、読み取りで確認する。

## 5. ロールバック（Worker）

コードを直さずに、以前のバージョンへ戻す。コマンドと注意は [Cloudflare へのデプロイ](cloudflare-deploy.md) の「ロールバック」。

- **D1 のデータとマイグレーションは、戻らない。** 戻るのは、Worker のバージョンだけ。
- ロールバックしても、`production` に次のコミットが反映されれば、最新に戻る。不具合を直す前は、反映を止める。
- 戻したあと、`/api/version` の `id` で、切り替わりを確認する（反映に 3〜9 秒かかる）。
- 恒久的に戻すときは、Git で `git revert` し、通常のデプロイの流れに乗せる。

## 6. D1 の復旧（Time Travel）

誤更新・破損のとき。**公開後は、書き込みを止め、現状を保全してから、行う**（時点復元は、その後の正当な登録・更新も失うため）。

**戻す先は、「破損が起きる前」の時点。** 障害のあとに取った「現在のブックマーク」へ復元しても、破損した状態に戻るだけ。

```bash
cd app
# 1. 復元前の状態を控える（復元を取り消したいときの戻り先）
npx wrangler d1 time-travel info DB
# 2. 破損が起きる前の時刻のブックマークを調べる（時刻は ISO 8601 など。詳細は `npx wrangler d1 time-travel --help`）
npx wrangler d1 time-travel info DB --timestamp="<破損の前の時刻>"
# 3. 2. で得たブックマークへ復元する（上書き）
npx wrangler d1 time-travel restore DB --bookmark=<2. のブックマーク>
```

- **大きな操作（移行・一括更新）の前には、現在のブックマークを控える**（秘密情報ではない）。その値が、そのまま「破損の前」のブックマークになる。
- 復元は、データベース全体を、その時点へ戻す。**公開後の復旧は、行単位の差分で戻す前進修正を、まず検討する**（再 ETL による全置換は、公開後の登録を失うため行わない。方針は [移行計画（アーカイブ）](archive/cloudflare-d1-migration-plan.md) §9-3）。
- **保管している暗号化ダンプ（2026-10-11 時点）は、切り替え前のデータ**。現在の状態の復旧には使えない。

## 7. secret の更新

値は、画面に出さず、パイプで `wrangler` に渡す（シェルの履歴・チャットに残さない）。コマンドの例は [Cloudflare へのデプロイ](cloudflare-deploy.md) の「Secrets の登録」。環境ごとに**別の値**を使う。

| secret | 更新の影響・注意 |
| --- | --- |
| `AUTH_SECRET` | 変えると、**発行済みのセッションがすべて無効になり、全員が再ログイン**になる。漏えいが疑われるときに更新する |
| `CRON_SECRET` | Cron の Bearer。変えたら、Worker の secret だけでよい（Cron は Worker 内の内部呼び出しのため、ほかの設定は不要）。16 文字以上 |
| `RAKUTEN_APP_ID` / `RAKUTEN_ACCESS_KEY` | 楽天ブックス Web Service で再発行し、Worker の secret を更新する。「許可された Web サイト」の登録は、そのまま |
| `CALIL_API_KEY` | カーリルで再発行し、更新する |
| `AUTH_GOOGLE_ID` / `AUTH_GOOGLE_SECRET` | Google Cloud Console で更新し、Worker の secret を更新する。リダイレクト URI の登録は、そのまま |

- 登録の確認は、名前だけが表示される: `npx wrangler secret list`（本番）。
- **更新したら、ログイン・検索・Cron（次の定時の実行）が動くことを確認する。**
- Cloudflare の API トークン（Workers Builds が使うもの）は、D1 の編集権限が必要。権限を変えたときは、次のデプロイが成功するかを確認する。

## 8. デモ環境の運用

方針と構成は [デモ環境の方針と構成](demo-environment.md)。

- **更新**: `main` の確認済みの時点を、`git push origin origin/main:demo` で反映する。反映後、`curl https://mybooklibrary-demo.nyproducts.workers.dev/api/version` の `tag` を確認する。
- **初期化**: 毎日 JST 03:00 に、Cron が、架空のデータを作り直す。手動の初期化は、Cron の時刻の前後を避け、Cron と同時に実行しない（[デモ用 D1 への適用手順書](demo-apply-runbook.md)）。
- **管理者**: デモでは、管理者の操作をすべて拒否する。管理者機能は、README の GIF・スクリーンショットで見せている。
- デモに、実データ・実在のメールアドレスを入れない。

## 9. リポジトリ・アカウントの保護

**第三者が、リポジトリをクローン・フォークして、自動デプロイを起こしても、本番・デモのデータは、変更されない。**

- 自動デプロイの仕組み（Workers Builds）は、**所有者の Cloudflare アカウント内**にあり、所有者のリポジトリの `main`・`production`・`demo` ブランチを監視している。第三者のクローン・フォークへのプッシュには、反応しない。
- デプロイには、所有者の Cloudflare への認証が必要。`wrangler.jsonc` の D1 の ID は、秘密情報ではなく、認証にならない。認証情報（Cloudflare の API トークン、Worker の secret の `AUTH_SECRET` など）は、Cloudflare 側にある。手元の控え（`app/.env.local`、停止中の AWS の SSM など）もあるが、いずれも、リポジトリには入っていない（`.env*` は追跡対象外）。
- クローンした人は、自分の Cloudflare アカウントで、自分の D1 を作り、`wrangler.jsonc` の接続先を書き換えない限り、デプロイは、所有者の D1 へ届かない（所有者の認証がないため、そのままでは、デプロイ自体が失敗する）。
- 実データ（暗号化ダンプなど）は、リポジトリに入れていない（追跡対象外）。
- フォークからの PR では、CI（GitHub Actions）が走るが、**デプロイはしない**（CI は `wrangler deploy --dry-run` だけ。使う secret は標準の `GITHUB_TOKEN` だけ）。Workers Builds は、自動デプロイの対象ではないブランチの**プレビュービルドを、無効**にしている。自動デプロイされるのは、Worker ごとに決めたブランチ（`main` → ステージング、`production` → 本番、`demo` → デモ）だけ（[Cloudflare へのデプロイ](cloudflare-deploy.md)）。

**残る危険は、所有者のアカウントの乗っ取り**（`production` にプッシュされると、本番の D1 を書き換えるコードが、デプロイされうる）。次の対策をしている。

| 対策 | 状態 |
| --- | --- |
| GitHub・Cloudflare の 2 段階認証（2FA） | 有効（2026-10-18 に所有者が確認） |
| `main` ブランチの保護 | PR 必須・強制プッシュ不可・削除不可（GitHub の設定） |
| `production`・`demo` ブランチの保護 | **意図して、設定していない**。書き込み権限があるのは、所有者だけで、2FA で乗っ取りのリスクを下げているため。この 2 つは、プッシュで、自動デプロイされる。共同作業者を増やすときは、**強制プッシュと削除の禁止**（所有者の通常の早送りのプッシュは、そのまま使える）を、設定する |
| 共同作業者 | 所有者のみ（`gh api repos/<owner>/<repo>/collaborators` で確認できる） |
